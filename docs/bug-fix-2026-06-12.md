## A｜報帳單號歸錯月份 + 同時送件會失敗

### 問題在哪

`services/expense_service.py`，`_generate_serial_number` 函式。

### 為什麼是問題

**問題 1：時區錯誤**

報帳單號格式是 `EXP-YYYYMM-NNNN`，月份來自 `datetime.now()`。但 Docker 容器預設跑 UTC 時間，台灣是 UTC+8。

每天凌晨 0 點到 8 點之間（台灣時間），UTC 還停在「昨天」，所以這段時間送出的報帳單號會被歸到上個月。

例：6 月 1 日凌晨 3 點（台灣時間）送出的報帳，單號會是 `EXP-202505-xxxx` 而不是 `EXP-202506-xxxx`。

**問題 2：並發衝突重試無效**

系統有設計 5 次重試機制，但序號的產生放在重試迴圈**外面**。兩個人同時送件時：

1. A 和 B 同時查詢「目前最大序號」，都查到 0
2. A 和 B 都計算出 `0001`
3. A 寫入成功
4. B 寫入失敗（號碼重複）
5. B 重試——但因為序號只算一次，還是拿同一個 `0001`，繼續失敗
6. 5 次全部失敗，系統拋出錯誤

### 怎麼修正

**時區**：把 `datetime.now()` 改為明確指定台灣時區。

```python
# 修改前
prefix = datetime.now().strftime('%Y%m')

# 修改後
_TW_TZ = timezone(timedelta(hours=8))
prefix = datetime.now(tz=_TW_TZ).strftime('%Y%m')
```

**重試**：把序號產生移進重試迴圈內，讓每次重試都重新計算。

```python
# 修改前（序號只算一次）
serial = _generate_serial_number(db)
for _attempt in range(5):
    expense = Expense(serial_number=serial, ...)

# 修改後（每次重試都重新查 MAX）
for _attempt in range(5):
    serial = _generate_serial_number(db)   # ← 移進來
    expense = Expense(serial_number=serial, ...)
```

## B｜啟動時偷建資料庫表

### 問題在哪

`main.py`，第 125 行，`on_startup` 函式。

### 為什麼是問題

`Base.metadata.create_all()` 是 SQLAlchemy 的「一鍵建表」，它看現在的程式 Model 長什麼樣就直接在資料庫建表，完全繞過 Alembic 的 migration 流程。

現在兩套機制同時在跑，會造成：

1. **Migration 歷史失真**：你加了新 Model 但還沒寫 migration，`create_all` 在啟動時偷把表建好了。之後跑 `alembic upgrade head`，它看表已存在就跳過，migration 歷史斷掉。

2. **欄位補不進去**：`create_all` 只建不存在的整張表，不會對已存在的表補欄位。如果 migration 要加欄位，但 `create_all` 沒幫你補，等到 API 查詢這個欄位時才在 runtime 爆炸。

### 怎麼修正

移除 `create_all`，改為只做「資料庫連線確認」。Schema 管理完全交給 Alembic。

```python
# 修改前
@app.on_event("startup")
def on_startup():
    Base.metadata.create_all(bind=engine)   # ← 移除這行

# 修改後
@app.on_event("startup")
def on_startup():
    if not check_db_connection():
        raise RuntimeError("Cannot connect to database")
    logger.info("Database ready.")
```

### 部署注意事項

**這是本次修改中最需要小心的一項。**

部署前請先確認正式 DB 的 Alembic 狀態：

```bash
alembic current
```

- 如果有版本號 → 正常，執行 `alembic upgrade head` 後再部署
- 如果是空白 → 表示 DB 是 `create_all` 建的，Alembic 不知道現狀，需先執行：

```bash
alembic stamp head   # 告訴 Alembic「現在的 DB 就是最新版，不要動它」
alembic upgrade head # 之後再正常升級
```

## C｜圖片檔案描述符洩漏

### 問題在哪

`services/ocr_service.py`，`classify_and_extract` 函式，第 243 行。

### 為什麼是問題

**什麼是 fd（File Descriptor）**：作業系統的規定，程式每次打開檔案或建立網路連線，都要先「登記」，作業系統發一個號碼牌（fd）。用完要「歸還」。每個程式最多只能同時持有 1024 個號碼牌。

舊程式用 `Image.open()` 打開圖片後，沒有告訴作業系統「我用完了」，號碼牌就一直被佔著。

每次 OCR 辨識 → 洩漏 1 個號碼牌
服務跑幾週後，1024 個全部被佔滿
之後任何需要開檔案、建連線、寫 log 的操作都會失敗 → 服務崩潰

### 怎麼修正

改用 `with` 語法，讓 Python 保證「不管成功或拋例外，一定會還號碼牌」。

```python
# 修改前
img = Image.open(resolved_path)
response = await gemini.generate_content(contents=[img])
# ← 如果 generate_content 拋例外，img 就永遠不會被關

# 修改後
with Image.open(resolved_path) as img:
    response = await gemini.generate_content(contents=[img])
# ← 離開這行，fd 立刻歸還，不管有沒有例外
```

## D｜LINE 連線洩漏

### 問題在哪

`services/line_service.py`，`get_line_api()` 函式及其 4 個呼叫者。

### 為什麼是問題

**什麼是 ApiClient**：你的伺服器要和 LINE 伺服器講話，需要建立一條網路連線（TCP）。`ApiClient` 這個物件負責管理這條連線。

舊的 `get_line_api()` 每次都建立一個新的 `ApiClient`，用完就丟棄，但**沒有關閉連線**。每條沒關的連線都佔用一個 fd，和 C 的問題疊加，加速耗盡。

受影響的 4 個函式：
- `get_user_display_name()` — 查詢 LINE 使用者暱稱
- `reply_text()` — 回覆訊息
- `push_reject_notification()` — 推播退件通知
- `push_text()` — 主動推播訊息

（`setup_rich_menu` 和 `download_image` 原本就正確，不在此列。）

### 怎麼修正

移除 `get_line_api()` 函式，讓 4 個函式各自用 `with ApiClient` 確保連線關閉。

```python
# 修改前
def reply_text(reply_token, text):
    api = get_line_api()           # 建立連線，但沒有保證會關
    api.reply_message(req)

# 修改後
def reply_text(reply_token, text):
    with ApiClient(_line_config) as api_client:   # 進入時建連線
        MessagingApi(api_client).reply_message(req)
    # ← 離開時自動關閉連線，fd 歸還
```

## F｜換單／折讓會串到別人的發票

### 問題在哪

`services/relation_service.py`，`find_active_expense_by_invoice_number` 函式。

### 為什麼是問題

當使用者上傳換單或折讓單，系統會用發票號碼去找「原始那張單」，然後把兩筆串在一起，讓財務知道這是同一個換貨流程。

舊的查詢沒有限制「要找同一個人的單」，只要發票號碼相同、狀態是 `is_active=True` 就串起來，不管是誰的。

台灣電子發票號碼是 8 碼英數字，不同商家、不同使用者碰巧號碼相同是有可能的。一旦碰到，A 組的換單會被串到 B 組的舊發票上，財務沖銷算到別人頭上。

### 怎麼修正

在查詢條件加上 `user_id` 限制，只找同一個使用者的發票。

```python
# 修改前（不分人）
def find_active_expense_by_invoice_number(db, invoice_number):
    return db.scalar(
        select(Expense).where(
            Expense.invoice_number == invoice_number,
            Expense.is_active == True,
        )
    )

# 修改後（加上 user_id 過濾）
def find_active_expense_by_invoice_number(db, invoice_number, user_id=None):
    filters = and_(
        Expense.invoice_number == invoice_number,
        Expense.is_active == True,
    )
    if user_id is not None:
        filters = and_(filters, Expense.user_id == user_id)
    return db.scalar(select(Expense).where(filters))
```

呼叫方改為傳入使用者：

```python
# 修改前
original = find_active_expense_by_invoice_number(db, ref_inv)

# 修改後
original = find_active_expense_by_invoice_number(db, ref_inv, user_id=new_expense.user_id)
```

## G｜LIFF Session 與圖片永不清理

### 問題在哪

`services/liff_service.py` 缺少清理函式；`services/scheduler.py` 缺少清理排程。

### 為什麼是問題

使用者每次打開 LIFF 報帳頁面，系統會建立一個 `UploadSession`，並把上傳的圖片存到 `uploads/` 資料夾。

Session 雖然有 30 分鐘的過期時間（`expires_at`），但「過期」只是個狀態標記，**資料庫記錄和磁碟圖片永遠不會被刪掉**。

常見的廢棄情境：
- 使用者開了 LIFF 但網路斷線
- 使用者開了但沒按送出就關掉
- 使用者上傳到一半失敗

這些不完整的 session 會無限累積，`uploads/` 資料夾只進不出，長期下來磁碟被撐爆，服務就寫不了新圖片。

### LIFF 上傳流程說明

```
使用者開 LIFF
  → UploadSession 建立（status = "uploading"）
  → 圖片存進 uploads/，OCR 跑

使用者按「送出」
  → submit_session 呼叫
  → Expense + ExpenseImage 記錄建立（出現在後台）
  → UploadSession status 改為 "submitted"

使用者沒按送出、或中途失敗
  → session 停在 "uploading"，30 分鐘後 expires_at 到期
  → 圖片和記錄留在磁碟/DB，後台看不到（因為沒有 Expense 記錄）
  → 清理機制負責清掉這些廢棄資料
```

### 怎麼修正

**新增清理函式**（`services/liff_service.py` 末尾）：

找出所有過期且狀態為 `uploading` 或 `expired` 的 session，刪掉磁碟圖片，再刪掉資料庫記錄。狀態為 `submitted` 的 session 不會被清理（那些圖片是已送出報帳的一部分）。

**新增排程**（`services/scheduler.py`）：

```python
# 每天凌晨 3 點自動執行
_scheduler.add_job(
    _run_cleanup_liff,
    trigger=CronTrigger(hour=3, minute=0, ...),
    id="cleanup_liff_sessions",
)
```

### 部署注意事項

清理排程器依附在批次排程器上，必須確認 `.env` 有以下設定才會執行：

```env
ENABLE_SCHEDULED_BATCH=true
SCHEDULED_BATCH_TIMES=["09:00"]  # 至少一個合法時間
```

若 `ENABLE_SCHEDULED_BATCH=false`，清理 job 也不會跑，`uploads/` 一樣會無限成長。
